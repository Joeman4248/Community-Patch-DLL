# IPC build of the Community Patch DLL (branch `vox-ipc-5.4.8`)

This branch is Vox Populi 5.4.8's DLL with **Vox Deorum's connection service** ported in. It adds an optional
named-pipe channel that lets a program on the same PC receive the game's events and call Lua functions that
mods register. All of it sits behind the mod option `IPC_CHANNEL`, which defaults to 0. With it off, the DLL
behaves like stock VP 5.4.8.

Gameplay and AI aren't changed. This is a communication channel only.

## What this branch changes

Three commits on top of the tag `Release-5.4.8` (plus the hardening pass below):

1. **Port Vox Deorum connection service to VP 5.4.8**
   - `CvConnectionService.cpp/.h` and `CvConnectionSchema.cpp/.h`: a pipe server on
     `\\.\pipe\tmp-app.vox-deorum-bridge` (or env `VOX_DEORUM_PIPE_NAME`), with JSON messages separated by
     `!@#$%^!`.
   - `Lua/CvLuaSupport.cpp`: every `GameEvents` hook is also sent to the pipe as a `game_event`, non-blocking,
     before Lua sees it.
   - `CvDealClasses.cpp`: a `DealMade` event (with the traded items), which has no Lua hook of its own.
   - `CvGame.cpp`: the service starts with a game, shuts down with it and handles incoming messages during the
     game update. It also stores an event counter in the save's SaveGameDB.
   - `Lua/CvLuaGame.cpp`: new Lua functions `Game.RegisterFunction`, `UnregisterFunction`, `CallExternal`,
     `BroadcastEvent`, `ProcessConnectionMessages`, `IsExternalRegistered` and `GetCurrentTimeEpochMs`.
   - `CustomMods.*` and `NewCustomModOptions.xml`: the `IPC_CHANNEL` option.
   - `ThirdPartyLibs/`: ArduinoJson and msinttypes. Project files and clang build scripts updated.
2. **CI: download SDKs with curl.exe.** The workflow's `wget.exe` download came out corrupt on GitHub's runners.
3. **Drop the SetVoxDeorumMode call.** Vox Deorum uses it to hide VP's error dialogs; this build keeps them.

**Left out of Vox Deorum on purpose:** its reinforcement-learning capture, its tactical AI and flavor changes,
player pausing and `SetVoxDeorumMode`.

## Hardening (2026-11-08, branch `vox-ipc-hardening`)

A robustness pass on the port. Changes are in `CvConnectionService.cpp/.h`, plus `Lua/CvLuaGame.cpp` passing the
Lua state to `UnregisterFunction`.

- **Lifecycle.** All critical sections are created once in the constructor and deleted in the destructor (they
  used to be created in `Setup` and deleted in `Shutdown`, so a UI add-in calling `Game.RegisterFunction` during a
  save reload entered a deleted section and crashed the game). `Shutdown` now only clears data: registered and
  external functions (`IsExternalRegistered` no longer stays true after a reload), pending calls (async callback
  data is freed), paused players and queues, and it drops the private registry tables. It releases the game-core
  lock while fencing out an in-flight drain, which avoids a deadlock with a UI drain. `Setup` undoes its
  allocations if the thread can't start. Saving with no Lua state no longer crashes. `RegisterFunction`,
  `UnregisterFunction` and `IsExternalRegistered` are safe at any time, including in games without `IPC_CHANNEL`.
- **UI-thread pump.** If a UI add-in calls `Game.ProcessConnectionMessages` every frame (the Claude Bridge mod
  does, on `Events.LocalMachineAppUpdate`), the UI thread is the only one that runs bridge Lua (`lua_execute`,
  `lua_call`, async `CallExternal` callbacks) while it pumps. The game-core pump points (every game event,
  `CvGame::update`) then skip, and a game-core sync `CallExternal` wait still receives its own reply. The DLL
  can't take the engine's Lua lock, so Lua from the game-core thread could otherwise run at the same time as UI
  Lua. Without a pump for 2 s it falls back to the old behaviour.
- **Lua threads.** Each registered function gets its own Lua thread (`lua_newthread` from the registering context:
  same globals, own stack), anchored in a registry table. `lua_call` and `!PostProcessGameEvent` run on it, and
  async callbacks get a per-call thread. Calls no longer share the registering context's stack and never touch a
  torn-down context's state pointer. Re-registering just overwrites; `UnregisterFunction` clears through the
  caller's state.
- **Pipe I/O.** The pipe thread alone owns and closes the handle (`Shutdown` used to close it too). No message is
  dropped or split when the pipe is full (the write is retried from the same offset; a 0-byte non-blocking write no
  longer spins). `ERROR_MORE_DATA` reads continue instead of dropping the connection. Every complete incoming
  message is queued each iteration (the 100-message cap left messages stuck). No `FlushFileBuffers` (a stalled
  client wedged the thread). The read buffer is on the heap. On connect the DLL announces every already-registered
  Lua function (`lua_register`), so a bridge that connects late still learns them.
- **Results and conversion.** `lua_response` is serialized before the Lua results are popped (ArduinoJson keeps
  Lua string pointers, so popping first let Lua collect them). An overflowing response is reported as
  `RESULT_TOO_LARGE` instead of a silently truncated success. No full Lua GC after every response (it stuttered).
  Lua to JSON conversion has a depth cap of 32 and calls `lua_checkstack`, so deep or self-referencing tables no
  longer overflow the stack, and it uses raw table access (no `__index` metamethods). External-call replies are
  parsed into a buffer sized from the reply (they were limited to about 8 KB). `CallExternal` requests have 64 KB
  of nodes (was 8 KB) and report `ARGS_TOO_LARGE` instead of sending truncated args. A sync-call reply that lands
  right at the timeout no longer leaks. Call ids and event ids are thread-safe.
- **Not changed:** the sync `Game.CallExternal` timeout is still 1 s, so long replies (an LLM, say) must use the
  async callback form.

## Reliability (2026-11-09, branch `vox-ipc-reliability`)

Changes are in `CvConnectionService.cpp/.h`. Older bridges keep working: they ignore the new message types and
never get the silence check.

- **Bounded outgoing queue.** At 20,000 messages or 32 MB, new game events are dropped instead of queued (replies
  and other messages always queue). A dropped event doesn't trigger the 20 ms throttle sleep. When the queue is
  back under half, the client gets `{"type":"events_dropped","count":N}`. Before, a connected client that stopped
  reading made the queue grow without limit and slowed every event by 20 ms.
- **Stall watchdog.** A client that takes nothing from the pipe for 10 s while a message waits is disconnected (the
  queue is cleared on the next connect), so a hung bridge can't slow the game for long.
- **`hello` on connect**, before the `lua_register` announcements:
  `{"type":"hello","protocol":1,"build":"<CURRENT_GAMECORE_VERSION>","pid":..,"turn":..,"ping_interval_ms":5000,
  "silence_timeout_ms":30000,"stall_timeout_ms":10000,"max_queue":20000}`. `build` is the git describe string the
  DLL was built from. A new connection never gets messages queued for an earlier one.
- **Heartbeat.** Every 5 s the DLL sends `{"type":"ping","seq":n,"game_idle_ms":..,"ui_idle_ms":..,"queued":..,
  "dropped_total":..}`. `game_idle_ms` / `ui_idle_ms` are the time since the game core (`CvGame::update`) / the UI
  add-in last pumped (-1 = never): the pipe thread runs on its own, so pings keep coming while the game is frozen,
  and these fields tell a hang from a slow turn. A client may answer `{"type":"pong","seq":n}` (it must start with
  `{"type":"pong"`; pongs are handled on the pipe thread and never reach the game). Once a client has answered
  one, it's disconnected after 30 s without sending anything.
- **JSON output.** Control characters in strings are escaped as `\u00XX` (they went out raw, which strict parsers
  such as Node's reject; patched in `ThirdPartyLibs/ArduinoJson.hpp`). Lua numbers outside the int range are written
  with full precision (ArduinoJson kept 9 digits: `123456789012` became `1.23456789e11`), and so are number keys
  (keys beyond the int range all became `"-2147483648"`; fractional keys had 6 digits). Tested by
  `tests/vox-ipc/run.sh` (Linux, real Lua 5.1, ASan/UBSan; its README lists what's still known to differ).
- **Log level.** Default INFO: DEBUG used to log every message in full (snapshots of 100 KB+, some on the game
  thread). Set the environment variable `VOX_IPC_LOG_LEVEL=DEBUG` (or `WARNING`, `ERROR`) before starting the
  game to change it.

## House rule: automated workers and routes (2026-11-11, branch `human-worker-routes`)

Not part of the IPC port; a gameplay change. In `CvBuilderTaskingAI::AddRouteDirective`, a human player's
automated workers never build railroads and never replace a route with a lesser one (railroad → road).
AI players are unchanged. Workers still repair pillaged railroads (`AddRepairRouteDirective`).

## Build

```
gh workflow run build_vp.yml -R <your fork> --ref vox-ipc-5.4.8
```

**Use the MSVC artifact (`VP_MSVC_Release_*`).** The clang release build doesn't load: GameCore.log shows
"LoadLibrary failed with error 1114" and the game crashes before the main menu. Vox Deorum hit the same problem
and turned clang optimizations off.

## Install

1. Back up the stock `CvGameCore_Expansion2.dll` in `(1) Community Patch` (and the copy in a modpack, if you use
   one).
2. Copy in the built DLL and update its md5 in `(1) Community Patch`'s `.modinfo`.
3. Set `<Row Class="3" Name="IPC_CHANNEL" Value="1"/>` in
   `(1) Community Patch/Database Changes/NewCustomModOptions.xml`. In a modpack, the database comes from
   `Override/CIV5Units.xml`, so change the row there.
4. Load a game. The pipe `\\.\pipe\tmp-app.vox-deorum-bridge` should exist.

To undo, restore the stock DLL and md5. Saves stay compatible either way: the service only writes its event
counter, and only while `IPC_CHANNEL` is on.

## Using it safely

- **Don't use the `lua_execute` message.** It runs code on the game's core Lua state, which all mods share, and a
  test script there crashed the game. Have a UI mod register a function with `Game.RegisterFunction` and call it
  with `lua_call`.
- VP's DLL crashes the game when a game function gets an out-of-range enum (-1 / `NO_*` / `NUM_*`), and `pcall`
  can't catch it.

## Updating to a new VP release

Rebase this branch onto the new `Release-*` tag, fix conflicts (usually `CvGame.cpp`, `CvLuaSupport.cpp` and the
project files), build with MSVC, and check that a save loads and the pipe appears.
